# memlite 多进程与 NFS 实施计划

> 与 [支持方案](./concurrency-proposal.md) 配套。目标为级别 0、1、2，不含多主复制或服务化。
> **实施进度（2026-11-08）**：JS 端 M0–M3/M5 已完成，M4 代码与探针就绪但未在真实 NFS 验收；Rust 端未同步。本文件保留原始计划与验收项，实际勾选状态以 [concurrency-progress.md](./concurrency-progress.md) 为准。
> 总估算：**15～19 个工作日**，不含等待真实 NFS 测试环境的时间。
> 顺序约束：M0 → M1 → M2 → M3 → M4 → M5。不得因 M2 本地测试通过就提前开放 NFS。

## 里程碑与交付

| 阶段 | 目标 | 估算 | 发布门槛 |
|---|---|---:|---|
| M0 | 锁机制、代次与依赖 spike | 2～3 天 | 两端锁互认，NFS 假设与测试矩阵明确 |
| M1 | 级别 0：多读单写 | 3 天 | 快照读、受锁单写、压实/轮转回归通过 |
| M2 | 级别 1：本地多写者 | 4～5 天 | 多真实进程、跨语言、条件写和向量测试通过 |
| M3 | 客户端与同步适配 | 2 天 | Rust CLI/Web、JS 宿主与导入/同步无绕过路径 |
| M4 | 级别 2：NFS 验证与开放 | 3～4 天 | 至少一组双客户端 NFS 环境通过验收 |
| M5 | 文档、兼容与发布 | 1～2 天 | 支持矩阵、错误契约、迁移和回退说明完整 |

## M0：协议与平台 spike（2～3 天）

### 任务

- [ ] 在两仓建立相同术语：`Snapshot`、`data lock`、`vector lock`、`revision`、存储代次。
- [ ] 实测候选锁库在 macOS、Linux 的共享/排他锁、进程退出释放、非阻塞超时行为。
- [ ] 实测 Rust 与 JS 持锁互斥，不只验证各自语言的自锁。
- [ ] 核验 `fs-ext` 或替代品的 Windows 语义、Node 支持版本、预构建/原生构建、tsup ESM/CJS 打包；许可与维护状态留档。
- [ ] 核验 Rust `fs2` 或替代品的系统调用和 Windows 行为；两端最终采用互认的锁机制。
- [ ] 选择代次机制：本地文件元数据、协议提交序号或内容校验；实测轮转和压实后不复用旧代次。
- [ ] 确定向量 revision 的持久格式与崩溃恢复，不能把内存中的 revision 当作重启后仍可用的证据。
- [ ] 明确 sync 的快照提交、git 互斥与并发新增之间的边界。
- [ ] 研究目标文件系统的目录 fsync、rename 持久性；确定失败恢复步骤。
- [ ] 明确测试环境：本机 macOS、Linux CI、至少一台 NFS 服务端和两台客户端；记录 NFS 版本与挂载参数。
- [ ] 把 spike 结果回写方案：若无法跨语言互认，停在 M0，替换实现而非降级为无锁。

### 交付

- 最小锁适配接口、进程互斥探针、锁顺序与代次决策记录。
- 明确支持的本地平台清单；NFS 候选配置清单。
- 错误码与锁超时默认值定稿。

## M1：级别 0，多读单写（3 天）

### 任务

- [ ] `memlite-js/packages/core/src/store.ts`：稳定锁文件、共享读锁、排他写锁、快照加载和代次刷新。
- [ ] `respire-memlite/rust/src/store.rs`：实现相同协议，锁定读取和提交完整覆盖。
- [ ] 新增 Store 内部未加锁原语与外部受锁入口的清晰分层，禁止公开入口嵌套持锁。
- [ ] 把新增、更新、删除、改挂、显式 id 导入全部路由到统一提交入口；写前强制锁内重载。
- [ ] 压实改随机临时文件，替换/删除顺序符合方案；轮转纳入排他锁。
- [ ] `recall`、`list`、`show`、`tree`、`chain`、`status` 使用同一数据快照；跨代次不得拼接因链与正文。
- [ ] `memlite-js` 的项目级/用户级回退分别建立自己的快照与锁，不在两个库间持锁。
- [ ] `sync` 纳入排他维护锁；锁文件与临时文件不进白名单。
- [ ] 保持单写者默认配置和旧数据格式，输出“已提交”与“仅读快照”的可诊断状态。

### 验证

- [ ] 现有 Rust、JS 单进程测试全绿，bench 排序无回归。
- [ ] 多真实进程并发读与单写者循环写，所有读取结果可解析且为某一代次完整状态。
- [ ] 写入/读取期间反复压实、轮转，不丢已提交记录。
- [ ] 杀死持锁进程后可继续；权限不足、锁超时、IO 错误均失败并给清晰错误。
- [ ] 不在 NFS 上宣称支持；级别 0 验收只覆盖本地文件系统。

## M2：级别 1，本地多进程读写（4～5 天）

### 任务

- [ ] 开放 `mode=multi-process`，所有写者遵守锁内重读和提交。
- [ ] Rust 补 revision 读取、条件更新、条件删除、条件改挂；与 JS `STALE_VERSION` 语义一致。
- [ ] 未传 revision 的兼容 LWW 明确按锁内提交顺序生效；宿主 UI 编辑必须传 revision。
- [ ] 显式 id、父节点存在、防环检查统一基于锁内最新快照。
- [ ] `vectors.ts` 与 Rust `vectors.rs` 加向量锁、锁内重载和两文件一致性校验。
- [ ] 嵌入计算移出数据锁；写向量前核对记录 revision，过期结果不写。
- [ ] `reembed` 分批计算、逐批受锁提交，避免长任务占住数据锁。
- [ ] 日志并发写入与 git sync 互斥；日志失败不得回滚已提交的记忆。
- [ ] 增加多进程测试夹具：真实 spawn、可控屏障、固定输入、最终记录集合校验。

### 验证

- [ ] 8 个本地进程并发新增，所有 id 均保留且每条只有预期记录。
- [ ] 同显式 id 并发新增仅一个成功；同 revision 更新仅一个成功。
- [ ] 并发删除/更新/改挂/压实/轮转均有确定的锁内顺序与正确最终状态。
- [ ] Rust 与 JS 混合并发写，最终两端读取一致。
- [ ] 并发嵌入、更新、删除、reembed 后向量 id/偏移/版本不串位，缺向量按契约回退。
- [ ] 覆盖进程崩溃、锁竞争超时和非法 revision；不允许为通过测试而关闭校验。

## M3：宿主与操作入口收尾（2 天）

### 任务

- [ ] JS `Memlite.open/close` 管理快照生命周期；异步 remember/update 不留下脱离锁的写操作。
- [ ] DSH、Obsidian 导入导出经公共 Memlite 提交入口；共享实例和自开实例行为一致。
- [ ] Rust CLI 每个子命令、Web 的 recall/update/delete/compact/reembed/sync 全走锁协议。
- [ ] Web 编辑回传 revision；冲突要求用户重读确认，不自动覆盖。
- [ ] 配置原子写；新增配置校验非法枚举与超时范围。
- [ ] 识别并拒绝未升级的并发写者；文档说明 advisory lock 无法阻止外部直接编辑。
- [ ] 更新 `docs/compat.md`，描述新增锁文件、revision、并发保证和版本混用限制。

### 验证

- [ ] 常驻 JS 宿主与 Rust CLI 交错读写，下一次操作可见新提交。
- [ ] Web 与 CLI 同 revision 更新产生一个成功、一个结构化冲突。
- [ ] Obsidian 导入与 CLI 并发新增无丢记录；导出是一致快照。
- [ ] 同库并发 sync 互斥，无额外白名单文件或无关暂存内容被提交。

## M4：级别 2，NFS 受控读写（3～4 天）

### 任务

- [ ] 实现 `filesystem=nfs` 显式配置与存储类型检测；未声明的网络目录拒绝共享写入。
- [ ] 实现隔离目录探针：共享/排他锁、锁竞争、写后可见、rename、fsync、代次刷新。
- [ ] 禁止 NFS `local_lock` 等仅本机生效的挂载配置；识别并清楚报错。
- [ ] 若属性缓存导致代次不可见，实施方案选定的提交序号/校验机制，并重跑全部锁测试。
- [ ] 至少两种 NFS 客户端场景验证：同机两进程、两台真实客户端；优先 Linux 客户端。
- [ ] 定义断连/重连错误与人工检查流程，不自动重放结果未知的写请求。
- [ ] 发布支持矩阵：操作系统、NFS 版本、服务端、挂载参数、测试日期、结果和已知限制。
- [ ] 明确不支持 SMB、同步盘与其他网络文件系统；未测配置不属于默认支持范围。

### 验收

- [ ] 双客户端共享锁与排他锁互斥实测通过，非仅本机锁成功。
- [ ] 双客户端并发新增、同 id 条件写、读取刷新、压实/轮转和 sync 全过。
- [ ] 网络断开期间无虚假成功；重连后数据校验通过，不重复提交结果未知的写入。
- [ ] 任何探测或验收失败均阻止将该配置标为受支持。

## M5：发布与交付（1～2 天）

- [ ] README 和包文档区分“多读单写”“本地多进程”“NFS 受控”三种能力。
- [ ] 提供迁移步骤、版本混用限制、锁超时处理、备份与恢复操作。
- [ ] changelog、版本号与发布说明只写已验收级别，不提前标级别 2。
- [ ] 在干净 checkout 构建、测试、打包；原生依赖安装与打包是独立验收项。
- [ ] 默认发布顺序：级别 0 → 级别 1 → NFS 支持矩阵随真实环境验收发布。

## 完成定义与风险

### 完成定义

- 所有写入口无绕过锁的路径；快照、压实、轮转、向量、同步都有相应测试。
- Rust 与 JS 数据与锁协议一致，现有数据无需迁移重写。
- 级别 0/1 可在本地真实多进程运行；级别 2 有具体 NFS 环境证据，不以理论兼容替代。

### 主要风险与控制

| 风险 | 控制 |
|---|---|
| Node 原生锁依赖跨平台/打包失败 | M0 先 spike，失败则阻止发布并换实现 |
| 旧客户端绕过锁 | 明确不支持混用，提供升级与离线迁移，不宣称绝对防护 |
| NFS 属性缓存与锁差异 | 显式 opt-in、探针、双客户端验收、支持矩阵 |
| 异步向量覆盖新版本 | 向量锁、锁内重载、revision 核对、失败可重算 |
| 全库刷新影响延迟 | 测量冷读、热读和外部提交后刷新；首版先保正确性，再优化增量加载 |
| 嵌入慢导致锁等待 | 网络计算不持数据锁，分批 reembed，有界锁等待 |
