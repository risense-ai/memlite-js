# memlite 多进程与 NFS 支持方案

> 状态：**JS 端级别 0/1 已实施**（2026-11-08）；NFS 代码与探针就绪但未在真实 NFS 验收；Rust 端待同步。实施证据见 [concurrency-progress.md](./concurrency-progress.md)。
> 范围：级别 0（多进程读、单写者）、级别 1（本地多进程读写）、级别 2（NFS 受控读写）。
> 实施仓库：`memlite-js`（已实施）与 `respire-memlite`（待同步）；两端须遵守同一套锁和存储契约。
> 配套：[实施计划](./concurrency-plan.md)、[互通契约](./compat.md)。

## 一、目标与边界

### 1.1 能力分级

| 级别 | 目标 | 一致性保证 |
|---|---|---|
| 0 | 多进程并发读，最多一个写者 | 读取看到完整快照；写者通过同一协议刷新视图；读者不依赖轮询等待 |
| 1 | 本地多进程并发读写 | 同一数据目录的操作经协作锁串行提交；读可并发；同 id 更新支持版本冲突 |
| 2 | NFS 上的受控读写 | 在明确的平台、挂载与服务端前提通过实测后，沿用级别 1；不承诺任意 NAS 配置 |

级别 0 只承诺部署上有一个写入来源；底层写操作已经使用排他锁，意外的第二个写者不会无锁交错，但在多写者语义与测试完成前，不把它当作级别 1。级别 2 沿用级别 1：多个进程可参与，逐个提交，不是无锁并行写。

### 1.2 不在本期范围

- 不做多机同时无锁写、多主复制、自动冲突合并或离线多主同步。
- 不承诺 SMB/CIFS、WebDAV、SSHFS、对象存储挂载、iCloud/Dropbox 等同步目录。
- 不把 `git sync` 当实时锁；它仍是显式的跨设备同步机制。
- 不改为 SQLite，不引入常驻服务，不保证远程读进程的网络断线通知。
- 不保证不遵循协议的旧版本、外部脚本或直接编辑数据文件的进程可以安全混入。

## 二、现状与问题

当前 `memory*.jsonl` 为追加日志，打开时载入内存；`emb.f32` 与 `emb-ids.txt` 分开写；压实重写活跃文件并删归档。Rust 和 JS 均无完整跨进程锁。

JS 的 `refreshExternal()` 仅以 size+mtime 检测外部变化，且只覆盖部分条件写；无法消除“检查后、写入前”的竞态。嵌入是异步的，因此仅在 JSONL 追加函数加锁仍不足。

必须同时解决：

1. 检查父节点、版本、防环后，追加之前不能被另一个写者改变状态。
2. 压实和轮转期间不能存在其他读者或写者的文件操作。
3. 常驻读取实例要看到其他进程的提交。
4. 向量计算与向量文件更新要防止交错覆盖。
5. NFS 的缓存和锁实现差异必须可探测、可报错、可验收。

## 三、总体设计

### 3.1 协作式文件锁

在数据目录增加稳定、永不改名或删除的锁文件：

```text
data_dir/
├── .memlite-data.lock     # 数据快照读写锁：共享读、排他写
├── .memlite-vector.lock   # 向量写入互斥锁
└── memory.jsonl           # 原有数据格式保持不变
```

- 锁只约束遵守协议的客户端；不能阻止外部程序直接改文件。
- 每次锁操作使用独立打开的描述符/句柄。描述符释放即释放锁；不依赖删除锁文件或 PID 文件判活。
- 使用 OS 原生、进程退出自动释放的文件锁。不得使用“创建临时锁文件存在即代表持锁”的易留死锁方案。
- 数据快照采用读写锁：快照读取持共享锁；所有数据变更持排他锁。不能用一把互斥锁把所有检索也串行化。
- 固定锁顺序：需要双锁时，先数据排他锁、后向量锁。嵌入网络请求期间不持数据锁。
- 默认获取锁有界等待；超时、不支持、权限不足均明确报错。不得静默退回无锁写。

### 3.2 平台适配

两端使用同一系统锁机制，不能只各自实现互不相认的锁。

- Rust：引入并验证提供 Unix `flock` 与 Windows 等价整文件锁的适配层；候选 `fs2` 的整文件锁接口已查得，但最终版本与许可在 M0 核验。
- JS：采用同样的系统整文件锁适配；候选 `fs-ext` 已查得其 npm 元数据包含 `flock` 和原生构建，Windows 等价语义、Node 版本和打包兼容性须在 M0 spike 证实。
- 候选库未通过 spike 时，不发布级别 1/2；换为明确支持同一锁机制的实现。不得一端用 flock、另一端用互不相认的目录锁。
- NFS 仅支持经验证的服务端锁与挂载组合。Linux `flock(2)` 文档说明现代 NFS 可将其映射为字节范围锁，但仍依赖内核、挂载选项和服务端；`local_lock` 一类本地锁配置不可用。

### 3.3 数据快照与刷新

引入 `Snapshot` 与存储代次：

```text
Snapshot = 一致的 records/deleted + 活跃/归档文件代次 + 可选向量代次
```

- 打开时：持数据共享锁，完整加载 JSONL，记录代次。
- 每次公开读取前：持数据共享锁，检查代次；变化则在该锁内重新加载，并更新本进程 Store。
- 读取期间持有共享锁，直到该次快照构造完成。返回的快照在锁释放后仍保持内容一致；它是读取时点视图，不承诺之后永远最新。
- `recall` 的词面排序基于同一个快照。一次召回的因链、列表、状态与正文不跨两个代次拼装。
- 不以 mtime+size 作为 NFS 的唯一变化依据。M0 验证可用的稳定代次；若 NFS 属性缓存导致不可见，则用协议文件中的提交序号/内容校验，经目标环境实测选定。
- 进程内为同一数据目录串行化锁请求；不可重入、嵌套或升级锁。公开 API 不嵌套调用已持锁的存储原语。

### 3.4 提交事务

所有 JSONL 变更，包括显式 id 导入，必须走同一提交入口：

```text
获取数据排他锁
→ 重新加载最新数据快照
→ 解析 id、校验父节点/版本/防环/唯一性
→ 追加一条完整 put/del 记录
→ fsync 活跃文件
→ 必要时在同一把锁内轮转
→ 更新本进程快照与代次
→ 释放锁
```

具体语义：

- 新增：UUID 冲突、显式 id 冲突、父节点不存在均失败；锁内重检。
- 更新、删除、改挂：锁内重读再校验，不再以打开实例时的旧对象直接提交。
- 已传 `expectedRevision`：不一致返回结构化 `STALE_VERSION`，由调用者重读后决定重试或放弃。
- 未传 `expectedRevision`：保留兼容 LWW，但其“最后”以实际取得提交锁并追加的顺序为准；不声称无数据覆盖。UI 编辑一律要求版本条件写。
- 所有操作单条 JSONL 提交；压实作为独立的排他维护操作。多步 UI 流程不是一个隐式长事务。
- `memlite sync` 分两段：先取数据共享锁，生成并校验待提交的本地文件快照；释放后在 git 同步互斥区内执行 commit/rebase/push。若代次已变化则中止并重取快照，不得把未审核的并发新增混入已有提交。
- git 锁只序列化 sync，不能替代数据锁，也不能阻止 sync 期间的新增写入。级别 0 单写部署由写者协调 sync；级别 1/2 必须接受 sync 快照是时点视图。
- 锁文件、临时文件、向量文件继续排除在同步白名单之外。

### 3.5 压实与轮转

- 压实前取得数据排他锁并重载；临时文件名带随机后缀，避免多个客户端共用 `.tmp`。
- 临时文件 fsync 成功后原子替换活跃文件，再删除不再需要的归档；目录项持久化策略在 M0/M2 验证。
- 压实不缩小排他范围，不先删归档再替换活跃文件。
- 轮转必须在数据排他锁内；归档序号在锁内计算。写者已打开的旧活跃文件不得脱离锁继续写。
- 异常退出后启动时清理只属本协议的临时文件；不得删除无法确认归属的文件。
- 失败时保留原始数据或完整临时文件，报出恢复状态；不能返回成功。

### 3.6 向量一致性

保留现有向量格式与“向量可重算”的定位。级别 1 的保证是**不向其他协议客户端暴露错位文件**，不是业务记录与异步向量同时提交。

1. 主记录在数据排他锁内提交，提交成功后释放数据锁。
2. 在锁外调用嵌入服务，避免网络请求阻塞其他写者。
3. 取向量排他锁，重新加载 `emb.f32`、`emb-ids.txt` 和维度。
4. 校验目标记录仍存在、内容版本仍匹配，再写入并 fsync 两个文件。
5. 先写新向量槽，再写对应 id；失败留下可识别的尾部记录，由校验/重建处理。
6. 同一 id 的原地覆盖也在向量锁内；读者仅在向量共享锁内加载对应代次的向量，释放后使用不可变缓存计算。
7. 记录向量对应的记忆 revision。现有格式没有此字段，M0 须选定新增 manifest 或单向可重建映射；在兼容读写协议和恢复测试定稿前，不允许声称支持并发向量写。
8. 未升级读者仍可能读旧向量，这是旧版本混用的禁止范围，不能靠 manifest 给旧版增加隔离能力。

如果目标记录在嵌入返回前已更新或删除，不覆盖其向量；后续由 `reembed` 补齐。缺少向量允许回退 BM25，但向量维度、id 数或字节数不一致必须显式报错并停止语义索引使用，不能返回错位匹配。

### 3.7 检索日志与配置

- `memory.querylog.jsonl` 是辅助日志，不进入数据快照锁的读路径。
- 检索日志追加、查询统计与导出使用一致的日志快照协议；并发查询不能交错破坏行。同步仍只提交明确的日志快照。
- `memory.querylog.jsonl` 不进入主数据快照锁的读路径，日志失败只报告日志失败，不回滚记忆提交。
- 共享 `config.json` 的写入也要原子替换；嵌入密钥配置不因共享库而扩权或复制到其他客户端。

## 四、配置与错误契约

建议新增：

```json
{
  "concurrency": {
    "mode": "single-writer",
    "filesystem": "local",
    "lock_timeout_ms": 10000
  }
}
```

| 配置 | 值 | 行为 |
|---|---|---|
| `mode=single-writer` | 默认 | 使用协议锁保护快照和写操作，文档仍要求单个写入来源；兼容现有调用方式 |
| `mode=multi-process` | 级别 1 开放 | 允许多个协议客户端读写同一目录 |
| `filesystem=local` | 默认 | 支持本地文件系统 |
| `filesystem=nfs` | 级别 2 显式开启 | 先探测锁与可见性，通过才允许读写 |

- 检测到非本地文件系统且未显式配置 NFS 时，写入失败并说明原因；不猜测挂载一定安全。
- NFS 模式必须是“读已提交、单写提交”的模型，不能把它解释为无锁多主。
- 统一错误码：`LOCK_TIMEOUT`、`LOCK_UNSUPPORTED`、`STALE_VERSION`、`EXTERNAL_WRITER`、`SNAPSHOT_CHANGED`、`VECTOR_CORRUPT`；实现扩展 `UNSUPPORTED_FILESYSTEM`（网络盘未显式 opt-in）与 `NFS_PROBE_FAILED`（NFS 探针未通过）。
- 错误包含数据目录、操作、是否已提交主记录与建议动作；不包含记忆正文、token 或凭据。

## 五、级别实施定义

### 级别 0：多读单写

- 读快照、写提交、压实、轮转统一纳入数据读写锁。
- 多读者可并发，读者每次操作检查代次。
- 单写来源下，所有读者在下一次操作时看到新快照。
- 多个进程意外同时写也不会无锁交错，但部署承诺仍是单写者。

### 级别 1：本地多进程读写

- 在级别 0 基础上开放多写者队列式提交。
- 锁内重读与条件写保证父节点、防环、显式 id 和版本校验基于最新状态。
- 向量、reembed、导入、同步均纳入协议。
- Rust CLI/Web 与 JS 常驻宿主共用锁，跨语言互通实测通过。

### 级别 2：NFS 受控读写

- 只支持 Unix/Linux 客户端与已验证 NFS 服务端组合；首轮不包含 Windows 挂载 NFS。
- 需要共享锁、排他锁、写后读、原子 rename、fsync、属性缓存行为均通过验收。
- 探针不修改真实记忆：在隔离测试目录运行；对已有库的探测只能使用锁和无害元数据操作。
- 探针失败即拒绝该挂载用于共享写入，并建议本地目录+`memlite sync`。
- 文档公布实际测过的配置矩阵，而不是笼统写“支持 NFS”。

## 六、兼容、发布与回退

- JSONL 行格式、BM25/RRF 常量、因果树字段不变；锁文件是新增元数据。
- 老库首次打开只在需要时创建锁文件；不因打开只读实例而改动记忆正文。
- 新版本可与旧版**顺序、离线**互通；同库运行期间禁止旧版写入。
- 用 `meta.json` 的 `storage_protocol=1` 元数据标识参与锁协议的库；老版本没有该字段，检测到其活动写入只可做有限告警，无法做到绝对识别，文档须明确此边界。
- JS 侧新增 `emb-meta.json` 记录向量对应的记忆 revision；它不参与 git 白名单，Rust 可忽略。
- 默认先发布级别 0；级别 1 通过跨进程与跨语言测试后开放；级别 2 独立发布说明，不与级别 1 捆绑宣称。
- 锁不可用时提供“关闭实例/停止其他写者后离线操作”的恢复路径，不提供 `disable_lock=true` 作为常规运行选项。

## 七、验收标准

| 类别 | 必过用例 |
|---|---|
| 多读 | 多进程持续读时单写者提交，结果均为完整 JSONL 快照，无坏行、错挂或截断 |
| 多写 | 多进程并发新增全部保留；显式 id 只允许一个成功；父节点和防环在最新快照上判断 |
| 条件写 | 两客户端拿相同 revision 更新，只有一个成功；另一个得到 `STALE_VERSION` |
| 压实/轮转 | 与新增、读取、删除并发进行，提交记录不丢，无错误归档覆盖 |
| 向量 | 并发 remember/update/reembed 后 id、向量偏移与内容版本一致；无向量时可回退 BM25 |
| 异常 | 持锁进程被终止后其他进程可继续；锁超时、权限不足、注入 IO 错误均有明确失败 |
| 跨语言 | Rust 与 JS 交错写、读、条件更新、压实，最终快照一致 |
| NFS | 两台真实客户端验证互斥、写后可见、rename、fsync、断连恢复；每种公布配置各跑一轮 |
| 回归 | 现有单进程测试、数据兼容、检索 bench 与打包构建全部通过 |

测试以固定随机种子/输入和记录集合校验，不仅看“命令退出成功”。并发用例使用多个真实进程，而不是单进程内多个 Promise 模拟。

## 八、已核实依据与待验证项

- 已读当前源码：Rust 的 `store.rs`、`vectors.rs`、`web.rs`；JS 的 `store.ts`、`vectors.ts`、`memlite.ts`、`config.ts`、`sync.ts`。
- Linux `flock(2)` 手册确认：支持共享/排他锁，NFS 支持依赖系统与服务端；SMB 语义另有差异，因此不在本期范围。
- 已查 `fs2` 源码中的整文件共享/排他锁接口；已查 npm `fs-ext@2.1.1` 元数据，包含原生构建和 flock 关键词。
- 候选依赖维护状态、Windows 支持、Node 打包、实际 NFS 配置、目录 fsync 和代次方案尚未实测，列为 M0/M4 验收项，不预先承诺。
